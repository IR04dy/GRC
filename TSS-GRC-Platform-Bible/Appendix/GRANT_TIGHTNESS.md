## What the first run found

This file is regenerated from live state, so a repaired finding disappears from it. The
first run, 2026-07-26 on the dev tenant, found **one** section-A2 instance:
`REPORTING:WRITE` guarding `ReportScheduleController#create`, `#update` and `#runNow`
while held by zero of 57 roles — the entire write surface of scheduled reporting, 403 for
every persona, invisible because `PLATFORM_ADMIN`'s code bypass masks it and fail-closed
logs nothing. Repaired by **V321** (ORG_ADMIN + GRC_ADMINISTRATOR). Making those three
endpoints reachable then exposed a second defect behind them: `ReportScheduleService`
copied `name` and `description` but not `nameAr`/`descriptionAr`, so the API silently
dropped both Arabic columns. Nobody could have hit it — no request had ever completed.

Tightening these grants is **F2-13b**, not this script: each change needs a per-tenant
impact query first, because the same mistake has been made twice in the other
direction — F2-27's plan pre-committed to an AND-chain that would have 403'd 8 of 18
legitimate holders, and the grant table is what falsified it.

## What F2-13b has closed so far

**The first B1 row, 2026-07-29.** `WORKFLOW:WRITE` guarded
`WorkflowRequestController#approve` and `#reject` while held by **55 of 57 roles**, so a
VIEWER, a REGULATOR_VIEWER, an EXTERNAL_AUDITOR, a SUPPLIER_USER and all eight `*_INGEST`
machine accounts could approve any workflow request — in the engine **14 modules** route
their approvals through. `WORKFLOW:APPROVE` already existed and already guarded the same
act in three sibling controllers (`ApprovalRequestController#transition`, both
`ApprovalChainController` decisions, `WorkflowSubmissionController`), so this was an
inconsistency rather than a missing feature. Fixed by moving the two guards and by
**V324**, which grants `WORKFLOW:APPROVE` to the roles that already hold *some* module's
APPROVE **and** already hold `WORKFLOW:WRITE`: 3 → 17 holders. Decision authority on a
workflow request therefore went from 55 roles to 17, and the two guard sites moved out of
the `WORKFLOW:WRITE` row above (18 → 16) into the `WORKFLOW:APPROVE` cell (3/4 → 17/6).

⚠ **This report caught the fix's own first draft.** The draft used only the
already-an-approver-somewhere predicate, and regenerating the file added a section-B4 row:
**CHANGE_MANAGER · WORKFLOW · APPROVE · READ not held** — a human persona holding no other
WORKFLOW grant, given authority to decide records it could not list or open. B4 exists to
say that write-without-read is correct for a *machine*; for a person it is a 403 halfway
through a flow. Hence the second predicate, which also makes `WORKFLOW:APPROVE` holders a
strict subset of `WORKFLOW:WRITE` holders. **A grant migration is exactly where the
half-grant gets created, so V324 now throws if any holder lacks the module's READ.**

**Deliberately NOT changed**, so the remaining rows above are decisions rather than debt:

- `WORKFLOW:WRITE` stays at 55 of 57. After the split it means *participate* — create,
  send, respond, submit, resubmit — and a SUPPLIER_USER answering a vendor attestation or
  an ingest account raising a request needs exactly that. Revoking it to tidy the B1 row
  would break real flows. The B3 count of 20 therefore stands unchanged, and B3's own
  framing in B4 is why: for the eight machines these grants *are* least privilege.
- `/review`, `/close`, `/reopen`, `/escalate` keep `WORKFLOW:WRITE`. `reviewer_id` and
  `approver_id` are separate columns, so requiring APPROVE on `/review` would collapse a
  two-stage gate into one. Whether finalising should need approval authority is a fair
  question and not the reported defect; `WorkflowApproveAuthorityTest` pins all ten
  lifecycle endpoints so the answer stays chosen rather than drifted into.
- **Section C's dead permissions are untouched.** They guard nothing, so revoking them
  changes no behaviour and only shrinks a checkbox list; each needs the endpoint question
  answered first — is the permission dead, or is the *feature* missing its guard? That is
  the A1/F2-23 failure mode in reverse.

**The second B1 row, same day — F2-29, and it needed no grant change at all.**
`CHANGE:WRITE` at 42 of 57 was the next row down. Following F2-13b's rule — *verify the
endpoint reaches a decision before treating B1 membership as a defect* — it did:
`POST /api/v1/changes/{id}/transition` was guarded by `CHANGE:WRITE` for **every** target
status, including `EMERGENCY_APPROVED`, which is reachable in a single legal hop from
`DRAFT`. Live as `ranalyst`: refused **403** by `POST /{id}/approvals`, granted **200** by
the transition to `EMERGENCY_APPROVED` — the raiser approving their own emergency change,
`cabDecisionAt` stamped, no votes, no committee. Fixed in code
(`ChangeManagementService.DECISION_TARGETS`), and **no migration was needed**: all 9
`CHANGE:APPROVE` roles already held `WRITE` and `READ`, so V301's matrix was right and only
the endpoint disagreed with it.

Two things worth carrying to the third row (`AI:WRITE`, 41 of 57):

- **This report cannot see the fix.** The guard is enforced in the service, because the
  target arrives in the request body and no legible `@PreAuthorize` can read it. So the
  `CHANGE:WRITE` guarded-site count above still includes `/transition` and the B1 row still
  reads 42 of 57. That is not drift — it is the limit of an annotation scan, and the reason
  `ChangeDecisionAuthorityTest` exists. **A tight grant table is not the same as a tight
  platform**, in either direction.
- **A row's width did not predict the defect; the endpoint did.** `CHANGE:WRITE` at 42/57 is
  *narrower* than `WORKFLOW:WRITE` at 55/57 and carried the worse hole, because the question
  is never how many roles hold a permission — it is what passing that guard lets them
  decide. Ranking B1 by count puts these rows in the wrong order.

**The third B1 row is NOT a defect — `AI:WRITE`, 41 of 57, measured 2026-07-29.**
Applying the same rule closed it the other way, and that is the useful result. `AI:WRITE`
guards six AI draft *generators* plus `POST /api/v1/ai/suggestions/{id}/review`. Verified
live: the review moves the suggestion's own status `DRAFT` -> `ACCEPTED`, stamps a reviewer
note and writes an audit line — `relatedEntityId` null, **nothing propagated to any**
**record**. So the permission means *may use the AI assistant and triage its own drafts*,
41 of 57 is an appropriate width, and there was nothing to tighten. Two of the three B1
rows were real; this one was not. **Reporting that is the deliverable** — the rule earns
its keep by closing rows as well as opening them.

⚠ **But the module did hold a defect this report is structurally blind to (F2-50).** While
measuring the row, the two AI suggestion *reads* turned out to be `isAuthenticated()` —
asking for no permission at all — while `AI:READ` existed and was granted to 41 roles. A
`viewer` holding **no AI grant of any kind** was refused the write (403) and handed 10
board-summary drafts with the full executive posture summary (403 now). **This report ranks
permissions by how many roles hold them, so an endpoint that asks for *no* permission
appears in no row of it.** Sections A/B/C can say a grant is too wide, dead, or
half-issued; none of them can say a route forgot to ask. Treat the report as where to
start looking, never as the inventory of what is wrong.

**...except that section C was pointing at it all along, and this is section C's first**
**answered row.** `AI:READ` was one of the 15 above — catalogued, granted to 41 roles,
guarding nothing, *"a checkbox that is pure theatre"* in this report's own words. It
guarded nothing **because the two endpoints that should have used it asked**
**`isAuthenticated()` instead.** So the section C question — *is the permission dead, or is
the feature missing its guard?* — resolves here as **the feature was missing its guard**,
and the theatre was real in both directions: 41 roles held a checkbox that did nothing
while a `viewer` holding no checkbox read the content. The fix moves this file's own
numbers — section C 15 -> 14, guarded pairs 91 -> 92, guard sites 1432 -> 1434, `AI` row
`41/0` -> `41/2`. **Re-ask the remaining 14 the same way before revoking any of them.**

## Section C, swept — all 14 rows now have a verdict (2026-07-29)

Every row above was asked the F2-50 question — *dead permission, or feature missing its
guard?* — by scanning for file-returning handlers (the F2-27 ratchet's own definition:
`byte[]` / `ResponseEntity<byte[]>` / `Resource` / `StreamingResponseBody`) in each
permission's module packages, then reading every hit by hand. **Result: one defect, two
deliberate decisions, eleven genuinely dead.** Recorded here so nobody re-investigates.

- **`WORKFLOW:DELETE` was the defect (F2-51).** Three delete endpoints exist in the
  workflow packages and none used it. Two are *tighter* than it would be —
  `ApprovalChainController#deleteTemplate` (2 roles) and `ApprovalRequestController#delete`
  (PLATFORM_ADMIN only) — so repointing them here would **widen** them and they were left
  alone; their `hasAnyRole` form is F2-05's scope. The third,
  `WorkflowRecipientListController#delete`, ran on `WORKFLOW:WRITE` = **55 of 57 roles**.
  Fixed + **V325** (1 -> 12 holders, derived the V324 way).
- **`EVIDENCE:EXPORT` and `ADMIN:EXPORT` are dead BY DECISION, not by oversight.** Both
  modules do have a file endpoint, and both are documented entries on
  `ExportAuthorizationRatchetTest.ALLOWLIST` with stated reasons:
  `AttachmentController#download` returns one object the caller already resolved by id
  (requiring EXPORT would break inline previews across the 14 modules using attachments),
  and `CommitteeCatalogController#exportForm` returns a blank form template with no tenant
  records in it. **Do not 'fix' these two** — that is the allowlist working.
- **The other eleven have no file endpoint anywhere.** `WORKFLOW`, `INCIDENT`, `CAPA`,
  `REGULATORY`, `TPRM`, `CONTROL_LIB`, `SCM`, `AUDIT`, `INTAKE`, `PRIVACY`, `AUDIT_LOG`.
  Checked against the central `reporting/ExportController` too, which guards each register
  with **that register's own** module EXPORT (`RISK:EXPORT`, `COMPLIANCE:EXPORT`,
  `CHANGE:EXPORT`) — so these are not exports hiding under another permission, the
  feature simply does not exist. Each is therefore a **product** question, not a security
  one: build the export, or revoke the permission. ⚠ Revoking is a data change and needs
  the owner's explicit go-ahead; `PRIVACY:EXPORT` in particular looks like a missing
  feature rather than a spurious permission, given PDPL RoPA reporting.
