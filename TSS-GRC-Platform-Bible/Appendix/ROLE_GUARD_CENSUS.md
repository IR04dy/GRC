# Role-guard census — what `hasAnyRole` actually authorises

Generated by `Appendix/scripts/role_guard_census.py` from the compiled `@PreAuthorize`
set (`RoleGuardConversionRatchetTest` → `target/role-guard-sites.txt`) joined against the
live `iam.roles` / `iam.role_permissions`. Do not hand-edit: the next run overwrites it.
Narrative belongs in the script.

`hasAnyRole('X')` tests for the granted authority `ROLE_X`. There is no fallback and no
PLATFORM_ADMIN bypass — `ModulePermissionEvaluator` is never called, so the platform
administrator passes a role guard only when the guard names a role they hold. A guard
whose every named role is absent from `iam.roles` is therefore not tight; it is closed to
everyone. Neither existing measurement can see that: the authorization ratchet counts a
role guard as guarded, and `GRANT_TIGHTNESS.md` joins permissions, which a role-only
guard names none of.

## B2. Pure role guards left admitting PLATFORM_ADMIN alone — by attrition

These are section B one notch weaker, and they are where this platform actually sits.
The guard names several roles; all but `PLATFORM_ADMIN` are absent from `iam.roles`; so the
feature is administrator-only, and the persona the module was built for cannot use it —
silently, because a 403 from a role guard is indistinguishable from a 403 that was meant.

Guards that name `PLATFORM_ADMIN` **and nothing else** are excluded: that is a stated
decision (settings reset, token revocation, platform administration) and belongs in a
different conversation. The distinction is invisible in the code, which is why it is
computed here rather than eyeballed.

## E. Permissions spelled as raw authorities

expression: `ModulePermissionEvaluator` is never invoked, so its hardcoded PLATFORM_ADMIN
bypass does not apply. The platform administrator passes only if PLATFORM_ADMIN holds that
permission as an actual grant row — which is a different question from the one the other
1,400 guards ask, and is answered per row below.
