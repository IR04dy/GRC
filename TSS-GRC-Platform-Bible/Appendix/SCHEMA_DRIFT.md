## 1. Is production a copy of development?

**Yes, on the evidence.** 94% of shared tables carry identical row counts and there
are **no dev-only tables** — a schema that had evolved independently would have both.
Consequence for any orphan or provenance audit: **prod's data IS the demo data**, so
classifying existing rows by provenance proves nothing. The only trustworthy evidence
is a clean-tenant probe.

## 3. Packaged on disk but not applied in production

Prod Flyway head is **V336**; highest file on disk is **V336**.

**279 migration files have no history row in production**, and the split matters more
than the total:

* **0 numbered ABOVE the 292 baseline** — simply pending; they run on the next restart:
  _none_
* **279 numbered AT OR BELOW the baseline — these will NEVER run.** Flyway treats
  anything at or under the baseline as already applied. Most are harmless: the restored
  dump already contains their effect. Listing all 279 would be noise, so §3b lists only
  the ones whose **stated intent disagrees with the schema that exists**.

### 3b. Baseline-skipped migrations whose intent the schema contradicts

For each never-running file, the `CREATE TABLE` / `DROP TABLE` targets are parsed and
checked against both databases. A row here is a migration that believes something about
the schema which is not true — the only subset worth a human's time.

| migration | intent | table | contradiction |
|---|---|---|---|
| `V247__drop_legacy_kri_tables.sql` | DROP | `risk.kri_readings` | **still present in prod (already gone from dev)** |
| `V247__drop_legacy_kri_tables.sql` | DROP | `risk.kri_breach_events` | **still present in prod (already gone from dev)** |
| `V247__drop_legacy_kri_tables.sql` | DROP | `risk.kri_definitions` | **still present in prod (already gone from dev)** |

⚠ **This is the defect class no filename ratchet can catch.** F2-49's
`MigrationFilenameRatchetTest` checks that names are well-formed and unique; these
files are both. Only comparing intent against the live schema finds them.

A `CREATE` contradiction means a capability may be shipped over a table that does
not exist — check for entities and routes before assuming it is dead code. A `DROP`
contradiction means a table the platform decided to retire is still carrying data
in production, and needs an idempotent re-issue above the baseline.

## 4. Cross-check to run next

This script compares two databases against each other and against the migration folder.
It cannot see the third party to the contract: **the code**. A table can be absent from
both databases while entities, controllers and UI routes sit on top of it — the
`bcm.crisis_comms_cascade` / `crisis_comms_template_v2` case, where `V172` creates them,
dev never ran Flyway and prod baselined past it, so a routed screen returns 503
`db-object-missing` for every caller. Run `table_xref.py` for that direction.

_Row counts come from `sys.partitions`, exact for tables with a clustered index. Every
table here has a primary key; the caveat matters only if a heap is ever added._
