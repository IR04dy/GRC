# ADR-016 — Documentation Governance: Status Headers, Supersession, and a CI-Enforced Register

**Status:** Accepted — closes the **document-governance** decision; makes **D-5** mechanical
**Date:** 2026-07-25
**Relates to:** `ADR-009` (registry as build artefact), `Appendix/DOCUMENTATION_REGISTER_AND_AUDIT_SUPPORT.md`
**Decision owner:** the platform owner. Recorded as the leader-aligned default on the owner's instruction;
this was the arrangement previously marked *provisional*.

## Context

The corpus, measured today: **335 Markdown files tracked in git, 353 on disk, 39 at the repository root,
of which 22 are competing `*_PLAN.md` documents.** 65% of tracked lines have not been touched since
2026-06-30 and nothing marks them historic. Generated documents — the 2,642-line
`TSS_GRC_PLATFORM_ASSESSMENT.md` among them — sit beside hand-written ones with no marking to say which
is which, so a reader cannot tell what an edit will survive.

Four measured failures, each a different mode:

1. **A wrong fact in a governing document propagated into scope for months.** `CLAUDE.md` listed **24**
   modules against a measured **58** — a 40% understatement that silently scoped 34 packages out of the
   RBAC catalogue, out of the test bar, and out of every remediation plan written against it. This is the
   most expensive documentation defect found anywhere in the review, and it cost more than any code defect
   in the register.
2. **Nothing says which of two generations governs.** The Saudi integration pack exists twice — 20 files
   at the root, 33 under `docs/` — and D-5 has stayed open purely because no rule exists to settle it.
3. **The register that was supposed to fix this went stale within days of being written.** Its census
   records 604 on disk / 331 tracked / 273 untracked; the 273 were phantoms in a stale git worktree that
   has since been removed, so the true figures are now 353 / 335 / 18. A register maintained by diligence
   decays at the speed of the repository. That is not a criticism of the register — it is the evidence
   that the control has to be mechanical.
4. **22 root-level plans, one of which supersedes most of the others,** with no supersession marking. A
   reader opening `MODULE_REVIEW_AND_REMEDIATION_PLAN.md` has no way to learn that
   `UNIFIED_IMPLEMENTATION_PLAN.md` governs.

## Decision

**Docs-as-code, one canonical document per subject, machine-checked.** Six rules:

**R1 — Every Markdown file carries a status header** immediately under its title:

```
**Status:** AUTHORITATIVE | GENERATED | HISTORIC | SUPERSEDED-BY `<path>`
**Owner:** <role> · **Last-verified:** <YYYY-MM-DD>
**Generator:** `<script>`        ← GENERATED only; the file is then never hand-edited
```

**R2 — Supersede, never delete.** A superseded document keeps its content, gains
`**Status:** SUPERSEDED-BY <path>`, and stays in git history. Deleting it destroys the audit trail of how
a decision was reached — and this repository's whole value proposition is that such trails survive.

**R3 — One canonical home per subject**, fixed:

| Subject | Canonical document |
|---|---|
| Agent working contract | `CLAUDE.md` |
| Business + functional + operational reference | `PROJECT_CHRONICLE.md` |
| Independent assessment, architecture, decisions | `TSS-GRC-Platform-Bible/` |
| The governing implementation plan | `UNIFIED_IMPLEMENTATION_PLAN.md` |
| Per-program history | the 21 other root `*_PLAN.md`, all marked `SUPERSEDED-BY` or `HISTORIC` |
| Deployment runbook | `DEPLOYMENT.md` |

**R4 — Generated documents are never hand-edited.** Fix the generator and regenerate. A hand-edit to a
generated file is silently destroyed on the next run, which is worse than being wrong.

**R5 — Every quantitative claim in a governing document cites the command that produced it.** The 24-vs-58
failure was possible only because a number had no provenance. `Appendix/MEASURED_BASELINE.md` already does
this; it becomes the standard for all four governing documents.

**R6 — The register is authoritative and CI-enforced.** `Appendix/DOCUMENT_REGISTER.csv` is regenerated by
`doc_register.py`, and a CI check fails the build when: a tracked `.md` is absent from the register, a
register row has no file, any `.md` lacks a status header, or a `SUPERSEDED-BY` path does not resolve.
Untracked `.md` files in the working tree are reported, not failed — that is how the 273 phantoms would
have been caught the day they appeared.

## Why this, with reference to the comparators

| Source | Practice | What it confirms |
|---|---|---|
| **ISO 9001 §7.5 / ISO 27001 §7.5** — *control of documented information* | Identification, version, approval, review, and **control of obsolete documents** | This is the auditable standard, and it is the one this product sells. R1, R2 and R6 are that clause, applied to ourselves |
| **Microsoft Architecture Center / AWS Well-Architected** | Versioned guidance, explicit last-reviewed dates, decision records separate from guidance | `Last-verified` is not decoration — a reader must know whether a claim was checked this month or in April |
| **ADR convention (Nygard / ThoughtWorks)** | Records are **immutable**; a changed decision is a *new* ADR that supersedes the old one | R2 is the ADR discipline generalised to all documentation. This ADR is itself an instance |
| **GitLab handbook · Atlassian docs-as-code** | Documentation lives in the repository, is reviewed in the same merge request as the code, single-source-of-truth is a stated policy | Docs reviewed apart from code are docs that drift. R3 fixes the "which document governs" question that costs new engineers the most |
| **Google engineering design-doc practice** | One canonical doc per subject, with an explicit pointer when replaced | Competing generations (D-5) are a documentation-lifecycle failure, not a content question |

The decisive argument is commercial. **This platform sells policy lifecycle management: version control,
review cycles, approval, supersession, and evidence that obsolete documents were withdrawn.** A vendor
whose own 335-document corpus has no version control, no review dates, no supersession marking and 22
competing plans is demonstrating, in its own repository, that it does not believe its own product
category. An acceptance committee that looks at the repo before the demo will notice. Fixing this is
therefore a **sales** control as much as an engineering one — which is why it earns an ADR rather than a
convention note.

**D-5 becomes mechanical.** The rule now decides: the two Saudi pack generations are reconciled by content
diff (W0-6), the newer-and-verified one becomes `AUTHORITATIVE`, the other gains
`SUPERSEDED-BY`, and neither is deleted. D-5 stops being a question about which files are better and
becomes a task with a defined output.

## Alternatives considered

- **Leave it; documentation is not the product.** Rejected on the measured evidence: the single most
  expensive defect in the entire review was a wrong number in a governing document, and it was expensive
  precisely because it was believed.
- **Move all documentation to a wiki or Confluence.** Rejected. It breaks review-with-the-code (the
  GitLab/Atlassian practice above), loses `git blame` provenance that the audit-support pack depends on,
  and puts the corpus outside the CI check that makes R6 work.
- **Delete the 21 superseded plans.** Rejected — this is the tempting cleanup. Each carries a §0
  implementation-status tracker recording what shipped and under which commit and migration; that is
  evidence, and `git log` is a poor substitute for a curated status tracker.
- **A `docs/` reorganisation with the root cleared.** Deferred, not rejected. Worth doing and it would
  churn every path referenced by 335 documents and every memory file. Sequence it after R1/R6 are enforced,
  so the register can verify the move rather than the move breaking the register.
- **Front-matter YAML instead of a Markdown header block.** Rejected for a small reason that matters:
  GitHub renders YAML front matter as a table in some views and hides it in others, whereas a bold header
  block is visible to a human reader in every renderer — including the auditor reading the file on GitHub.

## Trade-offs accepted

- Adding a header to 335 files is a large mechanical diff that touches nearly every document and will make
  `git blame` on line 3 of every file point at this change. Worth it once.
- `Last-verified` is only as honest as the person editing it. R5 (cite the command) is the mitigation:
  a claim with a re-runnable command can be checked by the reader regardless of the date.
- The CI check will fail builds for documentation reasons. That is the point, and it will occasionally be
  annoying at exactly the moment someone is trying to ship something else.

## Consequences

- Closes the document-governance decision; **D-5** is downgraded from a decision to a task under W0-6.
- Adds work: a header sweep over 335 files, the CI check, and a register regeneration. The sweep is
  scriptable for the status line and needs judgement only for `AUTHORITATIVE` versus `HISTORIC`.
- **The register must be regenerated now** — its census predates the worktree removal and is wrong by 269
  files in the "untracked" column. Its being wrong is the argument for R6, so it is stated here rather
  than quietly fixed.
- **Reversal cost:** trivially low. The headers are inert text; removing the CI check is a one-line
  revert. Nothing depends on this decision being permanent, which is the best argument for taking it now.

## Proof obligations

1. `py Appendix/scripts/doc_register.py` regenerates cleanly and the census matches
   `git ls-files '*.md' | wc -l`.
2. The CI check fails on a deliberately-added headerless `.md`, and on a `SUPERSEDED-BY` pointing at a
   non-existent path.
3. All four governing documents (`CLAUDE.md`, `PROJECT_CHRONICLE.md`, `UNIFIED_IMPLEMENTATION_PLAN.md`,
   the Bible's `README`) carry a status header and an owner.
4. Every root `*_PLAN.md` other than the unified plan carries `SUPERSEDED-BY` or `HISTORIC`.
