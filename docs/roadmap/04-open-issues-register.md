| 002 | **Refresh token revocation** — Current design has no server-side refresh token store. If a refresh token is compromised, it remains valid until expiry (7 days). Options: (a) store issued refresh token IDs in DB and check on use, (b) shorten TTL to 24h, (c) accept risk for v1.0. | MEDIUM | Architect | Resolved | Option (a) implemented. `platform.refresh_token` table (V181) stores one row per minted token with `jti` (UUID JWT-ID claim), `issued_at`/`expires_at`/`revoked_at`/`revoke_reason`/`user_agent`/`ip_address`, ROWVERSION, filtered indexes for "list active sessions" and "revoke all by user". `module/auth/refresh_token/RefreshTokenStoreService` issues / asserts-valid / revokes with rolling-refresh rotation on every `/api/auth/refresh` — captured-then-replayed old token fails on its next refresh because its row is now revoked. `AuthController.login` mints + persists; `AuthController.refresh` does jti lookup BEFORE signature verify + rotates + revokes old; `AuthController.logout` revokes by jti with reason `USER_LOGOUT`. New `RefreshTokenAdminController` exposes `GET /api/v1/auth/sessions` (mine), `DELETE /sessions/{id}` (revoke own), `POST /sessions/revoke-all` (logout everywhere), and admin-only `POST /sessions/revoke-user/{id}` (PLATFORM_ADMIN, suspected compromise). F7 audit + F8 events `REFRESH_TOKEN_ISSUED` / `REFRESH_TOKEN_REVOKED` / `REFRESH_TOKEN_BULK_REVOKED` on every mutation. Compromise-to-revoke window collapsed from 7 days to < 1 second. 12 service tests + 5 controller tests. |
